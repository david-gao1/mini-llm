# 迭代与发布流程

管理版本演进、技术债、持续改进。目标：**项目越做越好，而不是越做越乱**。

---

## 1. 迭代节奏

本项目按**周**为迭代单位（与课程节奏对齐）：

```
周一 ─── 产品角色 ─── 回顾上周 + 规划本周 REQ
         ↓
周一~周五 ── 开发角色 ── 按 REQ 实现
         ↓
周五 ─── 测试角色 ─── 回归测试 + 闸门验收
         ↓
周末 ─── 复盘 ─── 记录经验、清理技术债
```

**灵活调整**：一人全栈不必严格按天切角色，但每周至少完成一次完整的"产品→开发→测试"循环。

## 2. 版本管理

### 2.1 版本号规则

采用简化的语义版本：`v<主版本>.<迭代号>`

| 版本 | 含义 |
|------|------|
| `v0.1` | Part I 第 1 个迭代（tokenizer + data_loader） |
| `v0.2` | Part I 第 2 个迭代（attention + model） |
| `v0.3` | Part I 第 3 个迭代（train.py，闸门 M1 通过） |
| `v1.0` | Part I 完成，M1 闸门通过 |
| `v1.1` | Part II 第 1 个迭代（generate） |
| `v2.0` | Part II 完成，M2 闸门通过 |

### 2.2 打标签

闸门通过时打 Git tag：

```bash
git tag -a v1.0 -m "M1 闸门通过：预训练闭环"
git tag -a v2.0 -m "M2 闸门通过：训练→生成链路"
```

## 3. 分支策略

一人全栈场景下，保持简单：

```
main ─────────────────────────────────────→
  \                     /
   feat/m03-attention ─  （功能分支，完成后合回 main）
```

### 3.1 规则

| 规则 | 说明 |
|------|------|
| `main` 始终可用 | main 上的代码必须能跑通全量测试 |
| 功能分支开发 | 每个 REQ 或相关的一组 REQ 开一个分支 |
| 分支命名 | `feat/<模块>-<简述>` / `fix/<问题简述>` / `refactor/<简述>` |
| 合并前测试 | 合回 main 前必须全量测试通过 |
| 及时删除 | 合并后删除功能分支 |

### 3.2 什么时候直接在 main 上改

- 文档更新
- 配置微调（不影响代码行为）
- 紧急 bug fix（修完立刻测试）

## 4. 技术债管理

### 4.1 什么是技术债

代码中"先凑合，以后再改"的地方。常见来源：

- 为了赶进度跳过的错误处理
- 复制粘贴的重复代码
- 过时的注释/文档
- 缺失的测试用例
- 硬编码的配置值

### 4.2 记录方式

**代码中**：用 `TODO` 标记

```python
# TODO(P1-05): 当前只支持 cross_entropy，后续考虑 label smoothing
```

**集中管理**：每个迭代结束时，汇总所有 TODO 到一个清单：

```bash
# 查看所有 TODO
rg "TODO" src/ tests/ train.py --no-heading
```

### 4.3 清理策略

| 时机 | 动作 |
|------|------|
| 每个迭代结束 | 扫描 TODO，决定：修复 / 转为正式 REQ / 标记为"可接受" |
| 闸门验收前 | 清理所有阻塞性技术债 |
| 重构窗口 | 每 2~3 个迭代安排一次纯重构迭代（不加新功能） |

### 4.4 技术债红线

以下情况**必须立即处理**，不能欠债：

- 测试不通过（broken test）
- 接口契约不一致（HARNESS 里写的和代码不一样）
- 安全问题（硬编码密钥等）
- 构建/运行环境损坏

## 5. 迭代复盘

每个迭代结束时，花 10 分钟回答三个问题：

| 问题 | 记录位置 |
|------|----------|
| **这个迭代完成了什么？** | 对应 REQ 标记为完成 |
| **遇到了什么问题？** | 记录在迭代笔记中（可以是 commit message 或单独文件） |
| **下个迭代要改进什么？** | 更新流程文档或新增 REQ |

### 5.1 复盘触发的改进

| 发现 | 改进动作 |
|------|----------|
| 某类 bug 反复出现 | 增加对应的边界测试 |
| 某个流程步骤总被跳过 | 简化该步骤或合并到其他步骤 |
| 文档与代码不一致 | 在提交规范中增加检查项 |
| 某个模块频繁被改 | 考虑重构，提取稳定接口 |

## 6. 项目健康度指标

定期检查（不需要工具，人工判断即可）：

| 指标 | 健康 | 警告 | 危险 |
|------|------|------|------|
| 测试通过率 | 100% | 有已知的 skip | 有 fail |
| TODO 数量 | < 5 | 5~15 | > 15 |
| 文档与代码一致性 | 完全一致 | 有小偏差 | 严重过时 |
| 最近一次全量测试 | 今天 | 本周 | 超过一周 |
| main 分支可运行 | 随时可跑 | 需要小修 | 跑不起来 |

## 7. 与 AI 协作的迭代管理

| 场景 | AI 可以做什么 |
|------|---------------|
| 迭代规划 | 帮你梳理 REQ 优先级、评估工作量 |
| 技术债扫描 | 帮你搜索 TODO、分析代码质量 |
| 复盘辅助 | 帮你回顾 git log、总结本迭代的变更 |
| 重构建议 | 识别重复代码、过长函数、过深嵌套 |

## 8. 检查清单（迭代结束时）

- [ ] 本迭代计划的 REQ 已全部完成或明确延期
- [ ] 全量测试通过
- [ ] HARNESS.md 中的 REQ 状态已更新
- [ ] 新增的 TODO 已记录
- [ ] 如果达到闸门条件，已打 Git tag
- [ ] 复盘三问已回答
- [ ] 下个迭代的 REQ 已初步规划
