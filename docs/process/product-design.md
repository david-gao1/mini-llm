# 产品设计流程

从"一个想法"到"可执行的需求条目"的完整流程。目标：**想清楚再动手，写下来再开工**。

---

## 1. 流程总览

```
想法/问题
    ↓
[P1] 需求澄清 —— 这个功能解决什么问题？用户是谁？
    ↓
[P2] 可行性评估 —— 技术上能不能做？代价多大？
    ↓
[P3] 需求拆解 —— 拆成可独立交付的 REQ 条目
    ↓
[P4] 优先级排序 —— 先做哪个？依赖关系是什么？
    ↓
[P5] 写入 HARNESS —— 落到 HARNESS.md，含验收标准
    ↓
移交开发
```

---

## 2. 各步骤详解

### P1 · 需求澄清

回答三个问题，用一两句话即可：

| 问题 | 示例 |
|------|------|
| **解决什么问题？** | 模型训练后无法生成文本，需要推理/采样模块 |
| **用户/场景是谁？** | 训练完成后，想用 checkpoint 生成一段文本看效果 |
| **不做什么？** | 不做 beam search，不做流式输出 |

**产出物**：一段简短的需求描述（可以写在 Issue 里或直接写在 HARNESS.md 的备注中）。

### P2 · 可行性评估

快速判断：

- [ ] 技术上是否可行？（有无现成库/算法？）
- [ ] 依赖的上游模块是否就绪？（如生成模块依赖训练好的 checkpoint）
- [ ] 预估工作量：S（< 1小时）/ M（半天）/ L（1天+）
- [ ] 是否需要先做技术调研？（如果是，调研本身作为一个 REQ）

**产出物**：可行性结论 + 工作量预估，标注在 REQ 条目上。

### P3 · 需求拆解

将一个大功能拆成**可独立交付、可独立测试**的小条目。拆解原则：

1. **每个 REQ 对应一个可验证的交付物**（一个函数、一个模块、一个配置项）
2. **REQ 之间的依赖关系明确**（P1-04 依赖 P1-03）
3. **粒度适中**：太大了不好验收，太小了管理成本高；一般一个 REQ = 1~4 小时工作量

**拆解模板**（直接复制到 HARNESS.md）：

```markdown
| REQ-ID | 交付 | 契约要点 | Harness | 通过判据 | 依赖 | 预估 |
|--------|------|----------|---------|----------|------|------|
| P?-?? | 模块/函数名 | 输入输出约定 | 测试命令 | 可观察结果 | 前置REQ | S/M/L |
```

### P4 · 优先级排序

排序依据（按权重递减）：

1. **依赖链**：被其他 REQ 依赖的先做
2. **风险**：技术不确定性高的先做（早暴露问题）
3. **价值**：对闸门（M1/M2）贡献大的先做
4. **成本**：同等价值下，工作量小的先做

排完后在 HARNESS.md 中按顺序排列，或用标签标注优先级。

### P5 · 写入 HARNESS

按 `HARNESS.md` 中的需求模板格式，将 REQ 条目正式写入。必填字段：

| 字段 | 不能省 | 为什么 |
|------|--------|--------|
| REQ-ID | ✓ | 唯一标识，方便追溯 |
| 契约 | ✓ | 开发的输入，不能靠猜 |
| Harness | ✓ | 测试的依据，不能靠口头 |
| 通过判据 | ✓ | 验收的标准，不能靠感觉 |
| 依赖 | ✓ | 排期的基础 |

## 3. 与 AI 协作的产品模式

当你对 AI 说"我现在是产品角色"或"帮我做需求分析"时，AI 应该：

| AI 行为 | 说明 |
|---------|------|
| **追问而非假设** | 需求不清时主动问，不自作主张 |
| **帮你拆解** | 把模糊想法拆成结构化的 REQ 条目 |
| **评估可行性** | 从技术角度给出建议，但决策权在你 |
| **不写代码** | 产品阶段只输出文档和需求，不动代码 |
| **对齐 HARNESS** | 确保新 REQ 与现有体系一致 |

**典型对话示例**：

```
你：我想加一个学习率调度器
AI：好的，先澄清几个问题——
    1. 目标是什么？（更好的收敛？还是课程要求？）
    2. 用哪种调度策略？（cosine / step / warmup？）
    3. 这个改动影响哪些文件？（train.py？config.json？）
    → 建议拆成：REQ P1-05a（config 增加 lr_schedule 字段）
                 REQ P1-05b（train.py 实现调度逻辑）
    → 要我帮你写入 HARNESS 吗？
```

## 4. 需求变更管理

需求会变，但变更要有迹可循：

1. **小改**（措辞调整、判据微调）：直接改 HARNESS.md，commit message 注明
2. **中改**（新增 REQ、调整依赖）：先在对话中讨论，确认后更新 HARNESS.md
3. **大改**（推翻已有设计）：先评估影响范围，列出需要同步修改的文件清单，再动手

**禁止**：口头说"那个需求改了"但不更新文档 —— 这是屎山的起点。

---

## 5. 检查清单（产品角色完成时）

- [ ] 每个新功能都有对应的 REQ 条目
- [ ] REQ 条目包含完整的契约、Harness、通过判据
- [ ] 依赖关系已标注，优先级已排序
- [ ] HARNESS.md 已更新
- [ ] 如果涉及接口变更，相关模块的设计文档已更新
